Cloudflare Pages Setup
======================

Optional alternative host. The site currently runs on GitHub Pages via
.github/workflows/deploy.yml; both can build from this repo at the same time.

The only reason to move is HTTP response headers, which GitHub Pages cannot set
at all. That is what static/_headers is for -- it is copied into public/ and
ignored by GitHub Pages, and only takes effect on Cloudflare.

Full decision document, measurements and the two migration routes:
  private/docs/2026-08-29_cloudflare-pages-migration-decision.md

Build settings (Workers & Pages -> Create -> Pages -> Connect to Git)
---------------------------------------------------------------------
  Framework preset:       Hugo
  Build command:          hugo --gc --minify
  Build output directory: public
  Root directory:         (leave blank)

  Environment variable:   HUGO_VERSION = 0.158.0

Note: this repo IS the Hugo site -- hugo.toml sits at the root. There is no
hugo-site/ subdirectory; an earlier version of this file said there was, which
would have failed the build.

Watch for the "Build output directory" field. If the form does not ask for it,
you are in the Workers flow rather than Pages, and these settings will not
apply.

Going live on the custom domain
-------------------------------
Two routes, covered in detail in the decision document:

  Recommended: repoint the single `www` CNAME at the pages.dev hostname. The
  apex keeps redirecting because GitHub's redirect is driven by static/CNAME,
  not by DNS. No email records move. Reversible in minutes.

  Phase two: move nameservers to Cloudflare. Needed only for apex control or
  Cloudflare-side features. Carries every email record, and the registry's
  48-hour NS TTL means rollback is slow. Verify all eleven records before
  switching.

Rollback (either route): point `www` back at alexandrehefren.github.io. Leave
GitHub Pages configured and its custom domain in place -- that is what keeps
the fallback working.
